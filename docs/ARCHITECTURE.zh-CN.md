# 架构

English: [ARCHITECTURE.md](ARCHITECTURE.md)。

## crate 划分

这个仓库只有一个 crate：库。它不依赖本项目内任何其他 crate，因此可以在没有媒体库的机器上构建，也因此可以独立发布。

不属于协议的部分各自成仓库，一个决定一个仓库：

| 仓库 | 是什么 |
| --- | --- |
| `rust-airplay`（本仓库） | 发现、控制协议、配对、解密、组帧、时序、渲染器边界 |
| [rust-airplay-gstream](https://github.com/rust-airplay/rust-airplay-gstream) | 用 GStreamer 解码与播放 |
| [parlor-cli](https://github.com/rust-airplay/parlor-cli) | 命令行程序 |

后端依赖本 crate 并实现 `Renderer`；程序依赖两者。方向是单向的：这里不知道后端或程序的存在。

## 一次会话是什么样子

客户端通过 mDNS 找到接收端，向控制端口建立 TCP 连接，在上面说 RTSP。

1. `GET /info` 返回与广播相同的文本记录，因此客户端无论从哪边读到，看到的都是同一份广播。
2. `POST /pair-verify` 证明客户端持有它配对时得到的密钥。从未配对过的客户端走 `POST /pair-setup`，在那里 SRP 交换加上屏幕上的 PIN 证明用户就在设备旁边。
3. `POST /fp-setup` 是投屏客户端在发送加密视频之前要求的 FairPlay 握手。
4. `SETUP` 声明流。应答里带着接收端绑定的端口，请求里带着会话要用的密钥。
5. `RECORD` 开始播放。媒体随后从时序、控制、数据三个套接字到达，镜像画面从镜像监听到达。
6. `TEARDOWN`，或连接关闭，结束会话。

音频密钥与镜像标识正是会话要跨连接共享的原因。客户端在某次 `SETUP` 里发送音频密钥，之后的另一次 `SETUP` 里发送镜像流的 `streamConnectionID`，且不重复密钥。由于接收端按连接构建设置处理器集，按连接保存的状态会把密钥丢掉；因此密钥属于会话。

## 接收媒体

音频以 RTP over UDP 到达，每个包用 AES-CBC 解密（每条包重置），随后进入有界重排窗口。当序号缺失、而客户端当初声明过重传时，接收端会在控制套接字上请求补发；正是这个请求把丢包变成了可恢复。帧按序离开窗口；补不上的缺口被计数并跳过，少一个包的流仍继续播放。

镜像从 TCP 到达，包带 128 字节包头。一个包的密钥流是流上 key 与 IV 的 AES-CTR，而"字节从哪里取"是微妙之处：它从上一个包结束的地方开始，按整块读。长度不满最后一块的包会把该块的剩余字节留给下一个包，而这些字节在流里根本不存在，因为它们属于一块已经被读过的地方。计数器随后按该包自身字节填满的块数前进。这条规则写得这么具体，是因为有测试按已知包序列逐字节核对它；而把它当成普通计数器去读的版本，得到的是噪声而不是错误。

帧以 Annex-B 访问单元的形式离开媒体路径。单独发送参数集的客户端，其参数集会被拼到所属帧之前。

## 冲刷与暂停

客户端发 `FLUSH`，是在说"我接下来要播的不是屏幕上这一帧"——暂停后、拖动后或切换媒体后。
队列里的是旧画面，所以清空队列并递增代号；写入线程拥有渲染器的流，它注意到代号变化后
会调用 `flush`，已经取走的帧就是这样被丢弃的。

投屏客户端还会说明自己何时停止与恢复：codec 包的 option 字节（`0x56`/`0x5e` 停、
`0x16`/`0x1e` 恢复，`raop_rtp_mirror.c:580-586`）。这不等于"流暂时安静"——屏幕上的
画面就是它停下的那一帧。接收端会丢弃队列中的帧并报告这次转换；想让窗口冻结的后端可以
据此处理。

## 音画如何保持一致

投屏客户端发来的两条流，时间戳毫无共同点。镜像帧是 NTP 定点数，高位是设备开机以来的秒数（某次会话读到 8355），相邻帧相差约 1.43 亿个 tick，即 2^32 乘以 33 毫秒。音频帧是 RTP 计数，从随机值开始，在 44.1 kHz 下每帧前进 480 个采样。两者相减等于两个任意原点相减，任何绝对换算都差了数百万秒。

两条流真正共享的是**速率**。因此接收端各自以首帧到达为锚点，再按各自的速率推进：镜像每秒 2^32 个 tick，音频按采样率。客户端在同一瞬间采集两条流并一起发送，所以两个锚点只差一个网络传播时间，并保持这个差值。

做到这一点的不是时钟交换，而这是真机会话才确认的：它的应答只带整秒，延迟与偏移的量化误差就是一秒；而它报告的偏移是在定 epoch 的那次交换上按构造为零的残差。它保留下来是为了建立 epoch——把客户端时间戳换算成本地时间用于诊断——而不是用于排程。

两条写入路径的等待都有上限。客户端会在几十毫秒内送来一秒的镜像帧，若按采集间隔铺开，这批的最后一帧就要晚一秒才显示；超过四十毫秒就直接显示并移动锚点。视频默认完全不节流：投屏看的是画面跟手的快慢，需要均匀间隔时用 `pace_video` 换取。

## 渲染

帧以带时间戳的独立缓冲区跨过 trait 边界。接收循环绝不能等渲染器，因此每个流都由自己的线程写入，由队列供给。

视频队列有两个深度。流还在打开时——写入线程在第一帧才启动管线，解码器与窗口要花几百毫秒——队列允许涨到 120 帧：四分之一秒的未发送帧不是溢出，而在一个图像组里丢帧会让解码器引用它从未见过的画面。流开始播放、积压排空之后，队列保持 8 帧：放不下的帧意味着渲染器落后，最旧的一帧被丢弃，日志会说明画面可能在下一个关键帧之前受损。两个数字都存在，因为相反的两种做法都有可见的失败：打开期间丢帧会让画面花屏；而在启动积压还在队列里时切到稳态深度，会清空队列并要求客户端根本不发的关键帧，画面直接消失。

音频有自己的队列，原因相同，深度小得多：一个编码音频帧只有几百字节，而它的时间戳是渲染器用来节流的依据。

## 线程

`receiver::run` 是异步的，所有连接都跑在调用方的 Tokio 运行时上。阻塞性的工作有自己的线程：视频写入线程（持有渲染器的视频流）、音频泵（把帧推进 `appsrc`）、mDNS 广播，以及监视待定 PIN 的线程。因此渲染器在音频与视频线程之间共享，必须是 `Send + Sync`；它的流被移到写出它们的线程上，`push` 可以阻塞。

控制连接本身从不在渲染器上阻塞：它更新状态、应答请求，并把媒体标识交给拥有套接字的会话。

跨越边界的是**编码后的数据**，不是解码结果。视频帧是参数集已前置的 Annex-B 访问单元，因此后端只需要字节流解码器，不需要了解协议；音频帧是一帧一负载，因为 raw AAC-ELD 帧既无同步字也无采样率，字节流说不出它到哪里结束。`VideoConfig::codec` 说明帧的编码，它来自客户端在首帧之前发送的 codec 配置包——这也是视频流改在首帧打开、而不是连接建立时打开的原因。

解码与播放属于另一个仓库。这也是为什么写一个后端只需几十行：实现 `Renderer`、按 `codec` 选择解码器、把帧写出去。

## 发现

接收端同时注册 `_raop._tcp` 与 `_airplay._tcp`，并把当前客户端会读的文本记录填好。这些值不是装饰：例如 feature 位图的第 27 位决定客户端使用哪套配对协议。测试逐字段钉住了这些值，且它们取自运行中的接收端而不是头文件：头文件记录的是构建初值，程序在广播前可能改变它。

## 身份

身份是 32 字节种子。设备标识与会话使用的密钥都由它派生，因此一个种子就是一个接收端；配对过的客户端在重启后仍能认出它。客户端密钥在会话携带过它之后才被记住，这是诚实的边界：从未完成会话的客户端还没有证明任何事情。

库既不保存种子，也不保存客户端列表。持久化它们的程序让接收端可被认出；不持久化的程序得到的接收端每次都像是新的，对于一个不该记住任何东西的接收端来说，这是合理的选择。
